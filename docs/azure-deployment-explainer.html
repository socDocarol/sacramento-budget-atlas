Three identities, three different jobs

The employee badge, deployment robot, and runtime key are not interchangeable.

E

Employee badge

Lets an approved City employee sign in and open Budget Atlas.

Boundary: people and the approved access group.

D

Deployment robot

Lets an approved GitHub workflow update Azure after its checks pass.

Boundary: deployment changes allowed by Azure RBAC.

R

Runtime key

Lets the running Container App retrieve its container image.

Boundary: read-only image pulls from the registry.

Separation keeps a person, a release workflow, and a running service from borrowing one another's permissions.

Why are the identities separated?

Each identity receives only the access its job needs. If one boundary fails, the other two do not automatically inherit that access. The deployment identity can update infrastructure, the runtime identity can only retrieve an image, and employee access is checked separately by Microsoft Entra.

OIDC versus employee sign-in

Employee sign-in answers, "May this person enter Budget Atlas?" GitHub OIDC answers, "May this specific approved workflow make a limited Azure change right now?" Neither answer grants the other kind of access.

Temporary trust

OIDC is a temporary verified badge

GitHub proves which approved workflow is asking Azure for short-lived access.

  1. GitHub presents a temporary signed badge.
  2. Azure checks the repository and approved deployment context, including the expected environment, audience, and issuer.
  3. Azure issues a short-lived token to the deployment robot.
  4. Azure RBAC limits allowed changes.

The practical protection

No reusable Azure password is saved in GitHub. The proof is temporary and is accepted only inside the approved boundary.

OIDC does not

OIDC does not give employees access to Budget Atlas. It also does not automatically grant GitHub administrator access or permission to change every Azure resource.

Exact GitHub and Azure terminology

GitHub's workflow requests an OpenID Connect identity token. Azure validates the federated credential's issuer, audience, and subject, then issues short-lived access. Azure role-based access control, commonly called RBAC, defines which registry and Container Apps actions the deployment identity can perform.

Different moments, different authority

One-time setup versus a routine release

Administrators establish the boundaries once; routine releases operate inside them.

One-time setup

  • Obtain shared-platform approval.
  • Create a repository-specific deployment identity.
  • Configure its federated credential.
  • Make scoped role assignments.
  • Configure the Entra application.
  • Create or choose the employee access group.
  • Protect the GitHub environment.

Elevated resource or application ownership may be required here.

Routine release

  1. Choose a commit.
  2. Run tests and formatting.
  3. Build one immutable image.
  4. Create an SBOM.
  5. Scan the exact image.
  6. Exchange OIDC proof.
  7. Push by digest.
  8. Update the app.
  9. Wait for health probes.

A routine release should not require a human Azure administrator each time.

  • Reuse the shared environment, registry, and logging.

Release path

What happens when I press deploy?

Eight guarded steps move one tested image from GitHub to Azure.

Checkout

GitHub checks out the selected commit.

Python quality and tests

Lint, formatting, and the non-live test suite verify the code.

Tests stop before Azure login.

Immutable image build

Docker builds one image for this release.

SBOM and vulnerability scan

The exact image receives a software inventory and security scan.

A vulnerability gate stops before upload.

OIDC request

GitHub requests short-lived Azure access for the approved workflow.

Registry push and digest resolution

The scanned image is pushed, and Azure resolves its immutable digest.

Container App revision update

Azure updates only the image digest and revision suffix.

Health polling and traffic protection

Azure waits for startup, liveness, and readiness probes.

An unhealthy or timed-out revision leaves the prior single revision serving traffic.
